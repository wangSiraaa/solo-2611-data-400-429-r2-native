# 跨段可见性与安全局部压缩 — 设计说明

## 1. 数据模型与文件布局

| 文件 | 作用 |
| --- | --- |
| `manifest.json` | 当前有效 run 的 id 有序列表；不在其中的 run 不参与任何查询 |
| `<id>.json` | 不可变 run，点记录 `put(key,value,seq)` 与区间记录 `erase(lo,hi,seq)` 可混存 |
| `meta.json` | 该库曾导入的最大 seq，强制“新输入 seq 严格大于历史所有 seq” |
| `journal.json` | 每次 compact 的逐条保留/回收依据，供 `inspect` 复查，重开不丢 |

压缩替换时先写新 run 文件、再切 manifest、最后 unlink 旧 run 文件。撤下的 run
立即从磁盘消失，查询只遍历 manifest 中的 run，因此“已撤下旧 run 继续参与查询”
在结构上不可能发生。这里只处理正常进程内的持久重开，不涉及 WAL、掉电恢复或
并发提交。

## 2. 可见性：全局视角，禁止段内先过滤

逻辑规则只有两条，与 run 怎么切无关：

1. 每个 key 的候选值是**全库**所有 put 中 seq 最大者（winner）；
2. winner 可见，当且仅当 `winner.seq > max{ erase.seq : lo <= key < hi }`。

起点代码在每个 run 内部先做一遍删除过滤再跨段合并，等价于假设“同 key 的记录
都在一个 run 里”。一旦删除与被删点分居两段，未选段里的旧点就会绕过删除复活
（demo 的 `cross_run` 用例）。本实现把所有 run 的记录先汇总成
`{key: winner}` 与全局 erase 列表，再统一判定可见性，切段方式不影响结果。

### 扫描线实现（reader.py）

把每条 erase 视作 `[lo, hi)` 上的一个区间事件；按 key 升序遍历所有**实际出现
过点记录的 key**，用 `(-seq, hi)` 最小堆维护当前覆盖该 key 的区间：

- 遇到 `lo <= key` 的区间入堆；
- 堆顶区间 `hi <= key` 时弹出（半开区间，hi 处已不覆盖），惰性清理；
- 堆顶即覆盖该 key 的最大 erase seq。

复杂度 `O((P + E) log E)`，P/E 是点/区间记录条数。整个过程只访问真实记录和
区间端点，**没有任何与区间整数跨度成比例的步骤**；跨度 20 和跨度 2×10⁹ 的
erase 在 `cost_report.py` 场景 2 中计量出完全相同的 push/pop/事件数。

点查 `get` 走刺点路径：只找该 key 的 winner，再线性扫描覆盖该 key 的 erase，
不构造全库结构。库内有效物理记录上限 1000，点查成本上界即 O(1000)。

## 3. 压缩输出与安全回收（compactor.py）

设选中子集为 S，未选 run 集合为 U。

### 3.1 输出点：只做全局视角的版本淘汰

对 S 中的每个 put p：

- 若 p 不是该 key 的**全库** winner → 丢弃（已被更新的点版本覆盖）；
- 若 p 是 winner 但被某条 seq 更大的 erase 遮盖 → 丢弃（本就不可见）；
- 否则保留。

关键是 winner 与覆盖判定都用 S∪U 的全局信息计算，绝不把“删除已作用于 S 的
点”推广到 U。U 中的点原样留在 U 的 run 里，保护它们所需的 erase 见下。

### 3.2 输出 erase：按“是否仍保护未选段旧点”决定保留

对 S 中的每条 erase e（U 自己的 erase 留在 U 中不动）：

- 若 U 中存在点 p 满足 `e.lo <= p.key < e.hi` 且 `p.seq < e.seq`，
  则 e 仍在保护 p，**整条原区间保留**；
- 否则 e 没有任何保护对象，整条回收。

正确性论证：若不存在这样的 p，则 U 中落在区间内的点 seq 都大于 e.seq，本来
就不会被 e 遮盖（较新点不能被较旧区间误删）；而 S 中区间内还活着的点版本在
3.1 中已被证明可见（其 seq 大于所有覆盖 erase，含 e）。删掉 e 不改变任何
get/scan。反之只要存在一个受保护的 p 就保留，宁可保守、不做最优化。

全量压缩时 U 为空，任何 erase 都找不到保护对象，因此输出只含当前可见点、
不含任何删除记录——这是 journal 中可以直接检查的硬不变量。

### 3.3 压缩后继续写入

`meta.json` 让“seq 必须大于全部历史（含已被压缩撤下的记录）”在压缩后依然
生效。更晚的 put/erase 按同一逻辑历史解释：新 put 若落在保留区间内但 seq
更大则重新可见；新 erase 会在后续压缩中按 3.2 的同一规则参与回收。

## 4. 表示选择：原区间读时检查 vs 规范化覆盖片段

题目允许两种路线，本实现选择**保留 erase 原区间、读时扫描线检查**，代价用
`cost_report.py` 以真实记录计数展示。

### 重叠区间的影响

- 原区间表示：区间条数 E 就是存储条数；扫描线对每条 erase 恰好一次堆 push、
  至多一次 pop，重叠/嵌套只改变堆的瞬时大小，检查量随 E 线性增长（场景 1）。
- 规范化覆盖：先取全部端点切成原子片段，每段存一个最大 seq。N 条交叠区间
  最坏产生 2N−1 个片段；反复局部压缩每次都要重切，场景 4 实测 6 轮后
  原区间 6 条、规范化片段 11 条，膨胀随交叠累积。

### 更新（同 key 新 put）的影响

- 原区间表示：更新只动 `{key: winner}` 一个槽，erase 无需任何维护；
- 覆盖索引：片段本身不随 put 变，但片段上若冗余存了“每键可见性”就需要按
  key 维护，写放大更高。

### 压缩的影响

- 原区间表示的维护成本是一次“保护对象探测”：在 U 的点 key 上用二分定位
  `[lo, hi)`，再比 seq，O(|U| log |U|) 量级，与区间跨度无关；
- 片段表示每次压缩都要对保留区间重新切分并合并同 seq 邻接片段，片段数在
  局部压缩下单调累积，直到全量压缩才能清零。

### 结论

在“最多 16 run、1000 条物理记录、无快照并发”的约束下，原区间 + 读时扫描线
以 O((P+E) log E) 的线性级读取代价，换取零片段维护、零膨胀、压缩决策可逐条
解释；规范化覆盖更适合点查极密集且写入稀少的场景，本题不取。`inspect` 输出的
`read_work_measure` 把每次读取的真实 push/pop/比较次数暴露出来，可直接核对。

## 5. 入口与验证

- `add/get/scan/compact/inspect` 入口保留，CLI 见 `main.py`。
- `demo.py`：单段路径、跨段旧值误现的修复、只压缩 delete/fresh 后 10 号键
  仍被遮住。
- `verify.py`：独立字典模型（按 seq 逐条 put/erase 作用于普通 dict）对照；
  覆盖删后重插、多层交叠、半开端点、旧区间不删新点、部分压缩、全量清理、
  重新切段；固定种子历史 ×4 种切段 ×随机压缩顺序 ×压缩后再导入 ×重开目录，
  全部存活键逐一比对；并断言大跨度 erase 的扫描工作量与跨度无关、磁盘上只剩
  manifest 内的 run 文件。
- `cost_report.py`：第 4 节的四张实测计量表。
